# NARUTO印センサー

カメラに向かって印を結ぶと、忍術が発動するブラウザデモ。

> **これは個人が趣味で作った二次創作です。**
> 『NARUTO -ナルト-』は岸本斉史先生の作品であり、集英社および権利者に帰属します。

MediaPipe Handsで手のランドマークを取り、k-NNで十二支12印を分類する。
**15種の術を同時に待ち受け**ていて、順番の縛りはない。何の術を出すかは結び手が決める。

```
python -m http.server 8134
```

ブラウザで `http://localhost:8134/` を開き、「カメラ開始」を押す。

## 設計の芯: 静止で待たず、動きの切れ目で確定する

前の世代は「同じ印を1.5秒保持したら確定」だった。これだと豪火球6印に最低9秒かかり、
印を結んでいるというより検査を受けている感覚になる。忍者は静止しない。

現行版は**手が止まった瞬間に確定する**（静止100ms）。二度撃ちは時間のクールダウンではなく
「一度ほどくまで次を受け付けない」で防ぐ。これがそのまま **印 → 移行 → 印** という
本来のリズムになる。豪火球6印が約2.5秒で結べる。

もうひとつ、印を結ぶ枠（ROI）は廃止した。枠は誤爆防止の道具だが体験としては檻になる。
代わりに「既知の印からどれだけ遠いか」で"これは印ではない"を判定している。

## 術のレシピ

15種を同時待ち受け。画面右に全レシピが「あと何印か」付きで常時出る。

| 印数 | 術 |
|---|---|
| 3 | 分身の術 / 変身の術 / 雷遁・雷切 / 火遁・灰積焼 / 氷遁・狼牙雪崩の術 / イザナギ / 木遁・黙殺縛 / 白激の術 |
| 4 | 土遁・土龍弾 / 火遁・龍火の術 / 穢土転生 / 忍法・瓦手裏剣 |
| 5 | 口寄せの術 |
| 6 | 火遁・豪火球の術 / 火遁・鳳仙火の術 |
| **42** | **水遁・水龍弾の術**（ネタ枠。最速でも約20秒かかる） |

確定した印は履歴（最大6印）に積まれ、全レシピと末尾一致で照合される。
複数一致したら長い方を採る。最後の印から5秒空くと履歴は消える。

順番を間違えても履歴は捨てられない。結び直せばそのまま拾えるし、
途中で別の術に切り替えてもいい。

### レシピを追加するときの注意

`index.html` の `JUTSU_RECIPES` に足すだけだが、**必ず衝突を確認すること**。

- **完全重複**: 別々の術が同じ並びだと区別できない
  （水遁・黒雨は分身の術と同じ `未→巳→寅` なので入れていない）
- **途中暴発**: 短いレシピが長いレシピの部分列だと先に発動してしまう
  （外道・輪廻天生 `未→巳` は分身の術 `未→巳→寅` の2印目で必ず暴発するので入れていない）。
  **2印のレシピは基本的に避けたほうがいい**

現在の16本は全ペアで検証済み（完全重複なし・途中暴発なし）。

水遁・水龍弾の術は原典で44印だが、21印目と41印目の「壬」は十干（みずのえ）で
十二支ではない。このセンサーが認識できるのは12種だけなので、その2つを抜いた
42印にしてある。正しい印が判明したら足すこと。

なお印のレシピは出典によって食い違う。雷遁・雷切の `丑→卯→申` は確認済みの正解。

## 見た目

印の漢字と術名は筆書体（Google Fontsの Yuji Syuku）で表示する。数値やラベルは
読みやすさを優先してサンセット体のまま残している。

書体を変えるときは `index.html` の2か所を差し替える（head のフォント読み込みURLと、
`:root` の `--brush`）。候補は Yuji Syuku（端正）/ Yuji Boku（太くて墨っぽい）/
Yuji Mai（崩し気味）の3つ。ネットに繋がらない環境ではWindows/macの標準行書体に
フォールバックする。

## 認識のクセ（実測）

12印のleave-one-out k-NN精度は **98.6%**。認識そのものは十分で、
つまずくとしたら以下のクセによる。

**印ごとに"保持していても揺れる量"が8倍違う。** 印を保持したまま連写したデータで
フレーム間のランドマーク移動量を測ると、亥が0.3697に対し酉は0.0453。
亥は指が組み合って隠れるためMediaPipeの推定が定まらず、手を止めても止まらない。
一律のしきい値では亥だけ永久に確定しないので、`SIGN_SPEED_TOLERANCE` で
印ごとに実測比で緩めている（亥5.32倍、申1.65倍、丑1.37倍、他は1.0）。

**手の大きさの尺度は span を主役に、RMS半径で下から支える。** 速度は手の大きさで割って
カメラ距離の影響を消すが、その分母に手首→中指つけ根（span）だけを使うと、
亥のように手が潰れて見える印で極端に短くなる（中央値0.049。未は0.220）。
かといってRMS半径に丸ごと置き換えるのも誤り。RMSとspanの比は印ごとに0.69〜2.64と
バラバラで、置き換えると印ごとに違う倍率で速度が膨らみ、しきい値の意味が壊れる
（実際に巳が確定しなくなった）。`max(span, rms * 1.2)` なら底上げが効くのは亥と辰だけ。

**手数は1手/2手を行き来する。** 両手が重なると片手しか返らない挙動が印ごとに違う
（巳は93/7、子は2/98、未は53/47）。なので「両手が組まれているか」は発動条件に使えない。
また手数が変わったフレームは前フレームとの添字対応がずれるため、
そこだけ重心の近い順に1対1で対応付けている（手数が同じときは添字のままでいい。
重心で対応付け直すと巳や亥のように両手が重なる印で左右が入れ替わる）。

**カメラの縦横比が違うと認識が崩れる。** MediaPipeは x を画像の幅、y を高さで正規化して
返すので、**端末によって x:y の比が変わる**。normalizeHand は手の大きさで割る等方スケール
なので、この歪みは補正できない。PCで集めたデータをスマホで使うと崩れる（実測で
スマホ縦持ち相当の縦横比で 100% → 75%）。実際、辰・申・午・未が別の印に化けた。
対策として **y を実測の縦横比で割り、幅を単位とする等方座標に直してから**特徴量を作る。
学習データ側も `tools/rebuild_vectors.py` で同じ補正をかけ直してある。
これで縦横比を 0.5625〜1.78 まで振っても認識率100%を保つ。
`TRAIN_ASPECT`（index.html と rebuild_vectors.py）は学習時の縦横比で、
`data/signs.json` の `trainAspect` と一致している必要がある。
実際に届いている映像の解像度は画面の「カメラ」欄で確認できる。

**端末を増やすときはデータも増やす。** 縦横比を補正しても、レンズの歪みや
スマホを持つときの手の角度までは揃わない。k-NNは学習データにある見え方にしか
一般化しないので、実機で崩れる印が残ったらその端末で撮り足すのが正攻法。
収集ツールはサンプルごとにカメラの縦横比・解像度・UserAgentを記録するので、
複数の端末で撮ったデータをそのまま混ぜられる。

```bash
python tools/rebuild_vectors.py dataset/pc.json dataset/phone.json data/signs.json
```

**パーやチョキは印に化けうる。** k-NNは閉じた集合の分類器で「どれでもない」を返せない。
加えて片手検出だと特徴量104次元のうち45次元しか埋まらず、判断材料が半分になる。
対策として未知判定のしきい値を手数別にしている（1手は2.5、2手は4.0）。
より確実な対策は `tools/collect.html` の transition クラスに
パー・チョキ・グーなどを撮って「印ではない」を教えること（未実施）。

## 詰まったときは

画面の「確定を止めているもの」に理由が1つ出る。当てずっぽうで設定をいじる前にここを読む。

| 表示 | 意味 |
|---|---|
| 手が見えていません | MediaPipeが手を検出していない |
| 未知の形（距離 X > Y） | 既知の印から遠い。しきい値かデータの問題 |
| 印ではない形 | 棄却クラスと判定された |
| まだ動いています（速さ X > Y） | 静止判定に入っていない |
| 一度ほどいてください | 前の印から動いていない（二度撃ち防止） |
| 静止中 N/Mms | あと少し |
| 確信度不足 | 別の印と競っている |

## スマホで見る場合

`getUserMedia` は安全なコンテキストでしか動かない。PCの `localhost` では動くが、
スマホからPCのIPに `http://` でアクセスするとカメラが許可されないことがある。
HTTPSで配信するか、HTTPS対応のトンネルを使うのが確実。
