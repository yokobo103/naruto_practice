# これまでの経緯

いまの形に辿り着くまでにアプローチを2回変え、3世代目の中でもいくつかの手を試して外している。
その記録。**コードを読んでも「なぜそうなっていないか」は分からない**ので、
外した手とその理由をここに残す。

実物のファイル（旧デモ・学習済みモデル・旧サンプル・学習画像）は**ローカルの
`archive/` と `dataset/` にだけ**あり、リポジトリには入れていない。
学習済みモデルが2.1MB×2、旧サンプルJSONが3〜4MB、学習画像が267MBあり、
いまのコードから一切参照されないのに公開リポジトリを重くするため。

---

## 第1世代 — Teachable Machine（画像分類）

カメラ画像をそのまま画像分類モデルに通していた。MediaPipeは印の判定には使わず、
術の発動中に手元へエフェクトを出すためだけに使っていた。

千鳥（丑→卯→申）と火遁・豪火球の術の2本を実装し、学習画像を2820枚撮った。

**やめた理由**: 精度が上がらなかった。**着ている服や背景に判定が引きずられ**、
撮影時と違う服装だと途端に落ちる。画像分類である限り、手の形以外の情報を
モデルが勝手に使ってしまうのを止められなかった。加えて、印と印の**遷移状態**を
誤って拾う問題も解決できなかった。

（`archive/v1_teachable_machine/` の `index.html` は存在しない `./model/` を参照していて
この時点で既に壊れている。動かすなら後継の `chidori.html` を使うこと。）

## 第2世代 — MediaPipe + k-NN（静止1.5秒ホールド）

手のランドマーク（21点×手の数）から特徴量を作り、k-NNで分類する方式に変えた。
服装や背景の影響が消え、**精度の問題はここで解決した**（12印のleave-one-out精度98.6%）。

遷移状態の誤検出は、画面に「印を結ぶ枠（ROI）」を置いて、枠の中に手があるときだけ
判定することで無理やり抑えていた。

**やめた理由**: 認識精度ではなく**確定ロジックが体感を殺していた**。
「同じ印が1.5秒続いたら確定」だったため、豪火球6印に最低9秒かかる。
印を結んでいるというより検査を受けている感覚になっていた。忍者は静止しない。

## 第3世代（現行）— 動きの切れ目で確定する

**認識器は最初から十分だった**というのが出発点。「精度を上げる」方向は行き止まりで、
不自由さは確定ロジックの側にあった。変えたのは3つ。

1. **静止で待つのをやめ、手が止まった瞬間に確定する**（静止100ms）。
   二度撃ちは時間のクールダウンではなく「一度ほどくまで次を受け付けない」で防ぐ。
   これがそのまま 印 → 移行 → 印 のリズムになる。豪火球6印が約2.5秒。
2. **ROI（枠）を廃止**。枠は誤爆防止の道具だが体験としては檻になる。
   代わりに「既知の印からどれだけ遠いか」で"これは印ではない"を判定する。
   遷移状態の誤検出は、枠で避けるのではなく動きゲートで正面から解決した。
3. **順番待ちをやめ、術を同時に待ち受ける**。確定した印の履歴に全レシピを
   末尾一致させる。順番を間違えてもリセットされず、何の術を出すかは結び手が決める。

## 第3世代の中で試して外した手

ここが一番、記録しておく価値がある。どれも「良さそうに見えて実際は悪化した」もの。

### 速度のEMA平滑化 → 減速に追いつかず印を落とす

手の速さを指数移動平均で滑らかにしたが、**移行時に跳ねた値が閾値まで落ちるのに
4〜5フレームかかり、静止時間を食い潰す**。速度19まで跳ねた亥は、静止フェーズが
終わるまでに0.8まで落ちきらず、6印中3印が確定しなかった。

→ **直近2フレームの最大値**で判定する方式に変更。減速に一切遅れない。

### 手の大きさの尺度をRMS半径に全面置換 → 巳が死んだ

速度は手の大きさで割ってカメラ距離の影響を消している。その分母に
手首→中指つけ根（span）を使っていたが、亥のように指を組んで手が潰れて見える印では
極端に短くなる（亥0.049 / 未0.220）。

そこでRMS半径に丸ごと置き換えたところ、**巳が確定しなくなった**。
RMSとspanの比は印ごとに0.69〜2.64とバラバラで（巳2.64が最悪、卯1.32が最小）、
しきい値を据え置いたまま尺度だけ替えると、**印ごとに違う倍率で速度が膨らむ**。
体感していた「巳がダメ、丑と卯はいい感じ」は、この倍率の順と完全に一致していた。

→ `max(span, rms * 1.2)`。spanを主役に置き、潰れたときだけRMSで下から支える。
底上げが効くのは亥と辰だけで、他10印は倍率1.00＝元と完全に同一。
**単位を変えたらしきい値も合わせ直すこと。**

### 画面比での絶対速度による救済 → 正しい修正で不要になった

小さく写る印が不利になる問題に、絶対量での救済を足した。
しかし上のspan/RMSの正しい修正を入れたら不要になったので撤去した。
**前提が壊れているときに機構を足してはいけない。**

### 中央値による頑健化 → 揺れが分散していて効かない

亥の蠢きが「一部の指先だけ暴れているのでは」と考え、21点の平均でなく中央値を
使う案を検討した。実測すると**平均/中央値の比は1.03〜1.24倍しかなく、
揺れは21点に広く分布**していた。効かないので採用しなかった。

### 「両手が組まれているか」を発動条件にする → 手数が印ごとにバラバラで不可能

ROIの代わりに「両手の距離が近ければ印を結んでいる」で判定しようとしたが、
MediaPipeが手の重なりで片手しか返さない挙動が**印ごとに全然違う**
（巳93/7、子2/98、未53/47）。両手距離はゲートに使えない。

### 静止中に両手が見えたフレームを優先する → 巳が壊れた

両手で結ぶ印から片手が落ちると特徴量が45/104次元しか埋まらないので、
「静止中に一度でも両手が見えたら、そのフレームだけで決める」を入れた。
片手落ちの場面では確かに効いた（申 90%→95%、戌 85%→90%）。

**だが逆方向を検証していなかった。** 巳・辰・寅は9割方1手で検出されるため、
1フレームでも余計な手の誤検出が混ざると、良い片手フレームを全部捨てて
悪い方を信じてしまう。

  1手主体の印に余計な手が25%混ざる場面   巳 80%→50% / 辰 70%→65% / 寅 70%→65%

「なかなか確定しないし、確定したと思ったら誤判定」という体感どおりで、
誤判定はこの機能がONのときだけ出ていた（OFFなら誤判定0%）。差し引きマイナスなので撤去。

「両手が多数派のときだけ優先する」案も試したが、結果はOFFと完全に同一だった。
同様に「手数の多数派で揃える」「票をスコアで重み付けする」も試したが、
どちらも現状と同じ数字で、複雑にする価値がなかった。

**教訓: 片方向だけ検証して入れてはいけない。** この機能は「手が落ちる」場面しか
試しておらず、「余計な手が入る」場面を見ていなかった。

### 手の対応付けを常に重心距離でやる → 両手が重なる印で左右が入れ替わる

手数が変わったときに添字がずれる問題を、全フレームで重心距離による1対1マッチングに
することで解決しようとした。しかし巳や亥のように両手が重なる印では左右が入れ替わりうる。

→ **手数が同じなら添字のまま**（X座標順に並んでいるので対応する）、
手数が変わったフレームだけ重心マッチングを使う。

## 測って分かった数字

| 事実 | 数字 |
|---|---|
| 12印のleave-one-out k-NN精度 | 98.6%（n=1201） |
| 誤認しやすい組 | 寅↔未、巳↔子 |
| 印ごとの「保持中の揺れ」の差 | **8倍**（亥0.3697 / 酉0.0453、中央値0.0695） |
| 手のひら幅の印ごとの差 | 4.5倍（亥0.049 / 未0.220） |
| 片手検出時に埋まる特徴量 | **45 / 104次元**（2手なら98/104） |
| 1手サンプルのクラスタの締まり | k=5平均距離の中央値0.46、p95=2.01 |

**片手検出だと判断材料が半分以下になる**のが、パーやチョキが印に化ける根本原因。
さらにデータの「1手 寅」は片手の寅ではなく**両手の寅の片方が隠れたもの**で、
それは幾何学的に「指2本を立てた手」＝チョキそのもの。ここは原理的に分離できない。
未知判定のしきい値を手数別にして緩和している（1手2.5 / 2手4.0）。
より確実な対策は収集ツールの transition クラスにパー・チョキ・グーを撮ること（未実施）。

## 直したバグで印象的だったもの

### 印の履歴が時間切れで途中から欠ける

印を1つずつ「自分の古さ」で捨てていたが、残り時間バーは**最後の印からの経過**を
出していた。**バーが嘘をついていた**。

```
丑を結ぶ   t=0
卯を結ぶ   t=2.5s   バーは満タンに戻る（あと5秒に見える）
           t=5.0s   丑だけ消える（バーはまだ半分ある）
申を結ぶ   t=5.5s   履歴は 卯→申。雷切は成立しない
```

長い術ほど深刻で、**豪火球（6印）は印の間が1秒あるだけで不発**だった。
6印×1秒で合計5秒を超え、6印目に着く前に1印目が消えるため。
「やたらリセットされる」という体感の正体はこれで、実際にはリセットではなく
頭から静かに欠けていた。

→ 最後の印から一定時間空いたら**まとめて**捨てる方式に変更。

### 棄却クラスを候補から削除していた

`transition`（印ではない状態）を分類結果から**削除**していた。削ると、本当は
transitionが1位でも**次点の本物の印が繰り上がって当選**する。誤爆を止めるどころか
作る実装だった。順位に残して、1位に来たら確定を止めるのが正しい。

## レシピの罠

術を同時待ち受けする以上、レシピ同士が衝突しうる。2種類ある。

- **完全重複**: 水遁・黒雨は分身の術と同じ `未→巳→寅` で区別不能 → 外した
- **途中暴発**: 外道・輪廻天生 `未→巳` は分身の術 `未→巳→寅` の2印目で必ず発動 → 外した。
  **2印のレシピは構造的に危険**

`tools/check_recipes.html` を開けば全ペアを自動で検査する。レシピを触ったら必ず開くこと。

なお**印のレシピは出典によって食い違う**。千鳥は「丑」1個説・「子午申午卯」説があり、
baiduの雷遁・雷切「申→卯→丑」は正解の完全な逆順だった。鵜呑みにしないこと。
